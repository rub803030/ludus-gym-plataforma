2. OBJETIVO Y FLUJO PRIORITARIO
-------------------------------
Estabilizar el flujo operativo:

1. Propietario registra un gimnasio.
2. Verifica su correo y un administrador autorizado aprueba el gimnasio.
3. El gimnasio activo ofrece su codigo/QR real de afiliacion.
4. El socio crea su cuenta, verifica correo y se afilia al gimnasio.
5. Recepcion cobra un plan del gimnasio y genera la membresia correspondiente.
6. El socio presenta su QR temporal y recepcion registra el acceso.
7. El flujo mantiene datos, pagos y permisos aislados entre gimnasios.

El QR de afiliacion identifica al gimnasio; no es el QR temporal de acceso.


3. ARQUITECTURA Y REGLAS DE DATOS
---------------------------------
- Monorepo pnpm.
- API Node.js/TypeScript con Fastify, Prisma y PostgreSQL.
- Consola web Next.js/TypeScript.
- App Android Kotlin.
- Contratos y validaciones compartidos en packages/shared.
- GymMembership es la fuente de verdad de afiliacion y alcance local.
- Member.gymId permanece como dato legado/contexto de compatibilidad; no debe
  autorizar consultas, cobros ni accesos.
- Member.status representa la cuenta global; GymMembership representa la
  afiliacion a un gimnasio; Membership representa el plan pagado y vigente.
- Para permitir acceso se exige cuenta global activa, afiliacion local activa,
  gimnasio activo y plan vigente del mismo gimnasio.


4. DECISIONES FUNCIONALES ACORDADAS
-----------------------------------
- El precio del plan en el servidor es la fuente de verdad del cobro.
- No se aceptan descuentos arbitrarios no modelados.
- El reembolso total revoca la membresia vinculada dentro de la transaccion.
- Un pago legacy ambiguo no se reembolsa silenciosamente si puede sostener una
  membresia activa.
- El aforo se valida de forma comun y atomica para check-in QR y manual.
- Reintentar una solicitud de cobro identica devuelve el mismo pago; reutilizar
  la clave con payload diferente produce conflicto.
- Un fallo transaccional sin efectos no debe reservar permanentemente la clave
  de idempotencia.
- Los folios son consecutivos por gimnasio y anio mediante contador persistido.
- No ejecutar migraciones, publicar APK ni desplegar a produccion durante esta
  fase.


5. CAMBIOS IMPLEMENTADOS
------------------------
API y base de datos:
- El alta de recepcion crea Member y GymMembership en una transaccion.
- La afiliacion movil crea/reactiva la relacion local y establece el gimnasio
  activo; se rechazan cuentas, gimnasios o afiliaciones no elegibles.
- Listados, cobros, reportes, rutinas y nutricion aplican el alcance por
  GymMembership o filtros explicitos por gymId.
- La emision del QR y los check-ins QR/manual comparten las reglas de acceso.
- La capacidad del gimnasio se verifica dentro de la transaccion.
- La aprobacion de gimnasios requiere sesion ADMIN y verificacion del correo
  del propietario.
- Los errores QR diferencian credenciales invalidas de fallos de infraestructura.
- Los cobros derivan el importe del plan del servidor y crean su membresia
  asociada.
- Los reembolsos revocan la membresia vinculada y los casos legacy ambiguos se
  bloquean para revision.
- La idempotencia usa el pago persistido y clave unica por gimnasio.
- El folio se incrementa con un contador por gimnasio/anio.

Web y Android:
- La web presenta el QR/codigo real solo para el gimnasio activo/aprobado.
- El POS muestra el importe del plan como no editable.
- La UI conserva errores de API relacionados con afiliacion y aprobacion.
- Android conserva errores de escaneo y permite reintentar la afiliacion.
- No se genero una APK nueva. El codigo de version documentado previamente era
  versionCode 4 / versionName 0.2.0; verificarlo de nuevo antes de release.
