FLUJO OPERATIVO - LUDUS GYM (COPIA REDACTADA)
==============================================

Esta guia conserva orientacion tecnica general. Se omitieron credenciales,
tokens, correos personales, datos de cuentas de prueba e identificadores
privados. Los valores que hayan estado versionados deben considerarse
comprometidos y rotarse; esta sustitucion no los elimina del historial Git.


1. REPOSITORIO Y TRABAJO
------------------------
Repositorio: https://github.com/rub803030/ludus-gym-plataforma
Rama principal documentada: master.
Para estabilizacion, trabajar en una rama hotfix/release separada y nunca
editar directamente master. No hacer push, merge, release ni deploy sin
autorizacion del responsable.

Antes de trabajar:
    git status -sb
    git branch --show-current

No versionar archivos .env, llaves, keystores, tokens ni credenciales.
Inspeccionar los cambios antes de preparar commits y usar mensajes breves que
describan el cambio.


2. ESTRUCTURA Y COMANDOS
------------------------
Monorepo con pnpm y Turbo. Confirmar versiones desde los manifests del repo.

Comandos de validacion comunes:
    corepack pnpm install --frozen-lockfile
    corepack pnpm --filter @ludus/shared build
    corepack pnpm --filter @ludus/api typecheck
    corepack pnpm --filter @ludus/api test
    corepack pnpm --filter @ludus/web lint
    corepack pnpm --filter @ludus/web build
    git diff --check

Para validar todo el monorepo, revisar primero los scripts vigentes de la raiz.
Los chequeos Android requieren un JDK y Android SDK compatibles; comprobar la
version solicitada por Gradle antes de ejecutar el build.


3. DESPLIEGUE WEB
-----------------
El workflow de Vercel esta definido en .github/workflows/deploy-web.yaml.
Despliega a produccion en eventos configurados para la rama principal y puede
tener ejecucion manual. Verificar los triggers antes de cambiar o ejecutar el
workflow.

Los valores de Vercel y de la API deben residir exclusivamente en GitHub
Actions Secrets o en el gestor de secretos correspondiente. No imprimirlos en
logs, commits, tickets ni documentacion. No ejecutar el workflow como parte
de una estabilizacion sin autorizacion explicita.


4. API Y BASE DE DATOS
----------------------
La API usa PostgreSQL y mantiene migraciones SQL en
infra/supabase/migrations/.

Antes de ejecutar una migracion:
  - comprobar que la conexion apunta unicamente a staging;
  - verificar respaldo y estado de migraciones;
  - revisar el SQL y el impacto sobre RLS y datos existentes;
  - ejecutar solo las migraciones aprobadas;
  - comprobar conteos y flujos con cuentas de prueba.

El script scripts/apply-all-migrations.py aplica multiples migraciones y
semillas; no usarlo como sustituto de una aplicacion selectiva y segura.

Variables que pueden configurarse localmente (nombres solamente):
    DATABASE_URL
    DIRECT_URL
    RESEND_API_KEY
    SMTP_*
    EMAIL_FROM
    WEB_APP_URL
    EMAIL_VERIFICATION_TTL_MINUTES
    ADMIN_APPROVAL_EMAILS

No compartir valores de configuracion por chat ni agregarlos a Git.


5. REGISTRO Y AFILIACION
------------------------
El registro publico de gimnasio crea una solicitud pendiente. El propietario
verifica su correo y un administrador autorizado aprueba el gimnasio. Solo
despues de aprobarlo se activan su codigo y QR de afiliacion.

El socio crea primero una cuenta global y luego se afilia al gimnasio mediante
codigo o QR. GymMembership gobierna la afiliacion local; Member.gymId es legado
y no debe usarse para autorizar consultas ni accesos.

El acceso requiere cuenta activa, afiliacion vigente al gimnasio activo y plan
pagado vigente de ese mismo gimnasio. El QR de afiliacion y el QR temporal de
acceso son credenciales distintas.


6. ANDROID E IOS
----------------
Confirmar versionCode, versionName, firma y configuracion de SDK leyendo los
archivos del proyecto; no asumir que la APK publicada coincide con el codigo.

Antes de generar un release:
    - ejecutar pruebas y lint de Android;
    - compilar e instalar una APK de prueba;
    - verificar escaneo, afiliacion y errores de API;
    - incrementar la version solo con aprobacion;
    - no publicar en tiendas sin autorizacion.

La publicacion iOS requiere las herramientas, certificados y aprobaciones
propias de Apple. Revisar el estado actual de CI antes de atribuir un fallo de
esa plataforma al resto del release.


7. RELEASE Y SEGURIDAD
----------------------
- No aplicar migraciones ni desplegar contra produccion durante estabilizacion.
- No publicar APK, AAB ni IPA sin autorizacion.
- No poner credenciales, correos personales o datos de usuarios en documentos.
- Si un secreto fue versionado, tratarlo como comprometido: invalidarlo,
  rotarlo y coordinar con el responsable del repositorio la limpieza segura del
  historial; borrar el archivo en un commit nuevo no elimina versiones previas.
- Completar docs/QA.md y docs/STABILIZATION_PLAN.md antes de solicitar merge.
